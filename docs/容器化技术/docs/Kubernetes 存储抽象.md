# 容器的存储之困：从临时目录到持久化存储的三层抽象

## 1. 一个根本矛盾：容器生而短暂，数据却希望永存

用 `docker run` 启动一个 nginx 容器，在里面写几行文本到 `/usr/share/nginx/html`，然后删除容器再重新创建——你会发现之前写入的内容消失得干干净净。这不是偶然，而是容器文件系统的设计使然。

容器镜像由一系列只读层叠加而成。容器运行时（如 runc）在这组只读层之上创建一个临时可写层（通过 OverlayFS 或 copy-on-write 实现）。所有运行时写入都落在这个可写层上，一旦容器被删除，该层也随之销毁。更进一步，即使容器没有删除，**容器的重启也不会保留可写层中的内容**——新启动的容器总是基于镜像的只读层重建。这正是容器的"原罪"：容器被设计为无状态、可丢弃的进程沙箱，而不是持久数据的归宿。

然而现实世界中的应用很少是纯无状态的：数据库需要持久化数据文件，日志系统需要追加写入磁盘，缓存服务需要维护热数据，甚至一个简单的 Web 应用也需要保存用户上传的文件。容器的 ephemeral（短暂）本质与数据持久化需求之间存在一个根本矛盾。

Kubernetes 的存储体系，就是围绕这一矛盾展开的层层抽象。从挂载一个临时目录，到通过网络访问远端存储，再到自动按需供给——每一次抽象都是在解决更复杂的分布式的约束。

## 2. 第一层抽象：从容器内部突破到宿主机

### 2.1 emptyDir：与 Pod 同生共死的临时空间

最朴素的问题是：**Pod 内多个容器如何共享文件？**

假设你在 Pod 中运行两个容器——一个 Nginx 提供静态文件服务，另一个边车（sidecar）容器定时从 Git 仓库拉取最新内容并写入 Web 目录。这两个容器必须能读写同一个目录。

解决方法是 emptyDir。当你在 Pod 的 spec 中声明一个 emptyDir 卷时，kubelet 会在宿主机上创建一个空目录（具体可能是 `/var/lib/kubelet/pods/<pod-id>/volumes/` 之下），然后将这个目录挂载到所有声明了该卷的容器中。它的生命周期完全绑定于 Pod：

- Pod 创建时，目录被初始化（空的）。
- Pod 运行期间，容器可以向它写入数据。
- Pod 被删除时，目录内容一并被清除。

emptyDir 的名称本身就揭示了它的本质：**一个空的、临时的目录**。它是 Kubernetes 中最简单的卷类型——无需任何持久化后端，无需任何网络，纯本地文件系统操作。常见的用途包括：

- 容器间的数据交换（如 sidecar 模式）。
- 存放计算过程中间的临时文件。
- 用作缓存目录加速磁盘 IO（通过设置 `medium: Memory` 将其放在 tmpfs 上，变成纯内存存储）。

但 emptyDir 的生命周期严格绑定于 Pod。Pod 消失，数据即消失——在持久化的要求面前，它无能为力。

### 2.2 hostPath：把宿主机文件系统暴露给容器

当 emptyDir 无法满足需求时（例如 Pod 需要访问宿主机上的特定文件，或者容器需要日志从宿主机直接访问），我们需要更直接的控制。

hostPath 卷的作用很简单：**将宿主机上的任意文件或目录直接挂载到容器中**。它在 Pod 的 manifest 中指定一个主机路径，然后 kubelet 将该路径挂载到容器内。

使用场景包括：

- 读取宿主机系统信息，如 `/proc`、`/sys` 等。
- 让容器内的日志输出到宿主机统一目录，方便外部日志收集工具（如 fluentd）采集。
- 容器需要访问 Docker 守护进程，通过挂载 `/var/run/docker.sock`（尽管这是一种有争议的做法）。

hostPath 的缺点同样明显：**它引入了对特定节点的强依赖**。Pod 被调度到 Node A 上运行时挂载了 `/data/db`，如果 Pod 被重新调度到 Node B，Node B 上的 `/data/db` 是空的。更严重的是，如果多个 Pod 同时挂载同一 hostPath 目录，并发写入可能导致数据损坏——因为它没有任何锁定或隔离机制。此外，Pod 能够读取宿主机上的任意文件也会带来安全风险。

从设计哲学上看，hostPath 是 Kubernetes 存储抽象中的一个"反模式"：它打破了 Pod 的可移植性，将 Pod 与特定的节点绑定在一起。但有时候，它是解决问题的最直接手段——正是这种"必要之恶"，催生了更优雅的抽象。

### 2.3 第一层抽象的局限性

回顾 emptyDir 和 hostPath，它们解决了两个基本问题：**容器间共享文件**和**访问宿主机文件系统**。但它们的共同局限是显而易见的：

1. **数据绑定在 Pod 或节点上**。Pod 消失，数据就消失；节点故障，数据就丢失。
2. **无法跨节点访问**。Pod 被重新调度到不同节点后，先前的数据不可达。
3. **存储能力严重受限**。受限于宿主机本地磁盘的容量和性能。

当一个应用需要真正的"持久化"——即 Pod 被删除、重建甚至调度到不同节点后，数据依然可用——我们就必须走出本地文件系统的舒适区，进入**集群级存储**的领域。

## 3. 第二层抽象：从节点绑定到集群资源

### 3.1 问题的本质：调度与存储之间的张力

Kubernetes 的核心能力是调度：它会根据资源需求、亲和性约束、污点容忍等条件，将 Pod 分配到最适合的节点上。调度器（scheduler）的决策逻辑是**集中式的、动态的**——它不假定 Pod 会落在哪个节点上。

但存储恰恰相反：**数据天然地定位在某个物理位置上**，无论是本地磁盘、NFS 服务器还是云上的 EBS 卷。数据不会自动跟随 Pod "迁移"。

于是产生了一个经典的分布式系统张力：

> Pod 可以调度到任何节点，但数据只能在一个地方。

在集群存储环境中，"调度"和"存储"这对矛盾不能通过单向妥协来解决。如果我们让 Pod 总是绑死在某个节点上（使用 nodeSelector 或 hostPath），就等于放弃了 Kubernetes 调度的灵活性；如果我们让存储完全跟随 Pod，就需要一套机制来确保正确的 Pod 落在正确的节点上，并且正确的存储卷能被正确地挂载上去。

**PersistentVolume（PV）和 PersistentVolumeClaim（PVC）** 正是为此而生的解耦层。

### 3.2 PV 与 PVC：一个生产者-消费者模型

理解 PV/PVC 的最佳切入点是"声明式资源管理"——这是 Kubernetes 贯穿始终的设计哲学。

将 PV 类比为集群中的"存储资源池"，它是由管理员（或自动脚本）预先准备的一块存储单元。一个 PV 包含以下关键信息：

- **容量**：如 100Gi、1Ti。
- **访问模式**：单节点读写（RWO）、多节点只读（ROX）、多节点读写（RWX）。
- **回收策略**：PV 释放后的处理方式（Retain、Delete、Recycle）。
- **后端类型**：NFS、hostPath、云盘（EBS、PD）等实际的存储实现。
- **挂载参数**：文件系统类型、挂载选项等。

PV 是一个**集群级别的资源**，不属于任何命名空间。它独立存在，就如同集群中的 CPU 和内存一样，是可供 Pod 消费的"基础设施"。

而 PVC 是用户或应用对存储的"请求声明"。一份 PVC 描述：

- **所需容量**：比如 80Gi。
- **所需访问模式**：比如 ReadWriteOnce。
- **可选的 StorageClass**：指定要使用哪种类型的存储。

关键设计在于：**用户不关心 PV 具体是由什么后端构成的，也不需要知道它在哪里**。用户只需声明自己的需求（PVC），Kubernetes 负责将 PVC 与一个满足需求的 PV 进行**绑定（binding）**。绑定之后，Pod 通过 PVC 来引用这个存储卷，而不直接接触 PV。

这种生产者-消费者模式的意义在于：

1. **关注点分离**：集群管理员负责准备 PV（"我有什么"），应用开发者负责声明 PVC（"我要什么"），两者通过声明式匹配自动对接。
2. **解耦生命周期**：PVC 和 Pod 是绑定关系，PV 独立于 Pod 存在。即便 Pod 被删除，PV 和其上的数据依然完好无损。
3. **提升可移植性**：应用 yaml 中只需要写 PVC 的名字，不需要写任何与基础设施相关的路径或云厂商信息。从自建机房迁移到云上时，只需要在集群层面重新创建 PV，应用的 PVC 声明不需要改动。

### 3.3 绑定机制：一对一的契约

PV 与 PVC 的绑定遵循一一对应的原则：**一个 PVC 只能绑定一个 PV，一个 PV 也只能被一个 PVC 绑定**。匹配条件有三个：

1. **容量**：PV 的容量必须 >= PVC 声明的容量。
2. **访问模式**：PV 必须支持 PVC 要求的访问模式。
3. **StorageClass**：如果 PVC 指定了 StorageClass，PV 的 StorageClass 必须匹配（或者 PV 的 `storageClassName` 为空且 PVC 的 StorageClass 也为空，表示使用默认 StorageClass）。

绑定完成后，该 PV 被标记为 `Bound`，不再接受其他 PVC 的绑定请求。如果集群中没有符合条件的 PV，PVC 会持续处于 `Pending` 状态，直到有匹配的 PV 被创建或动态供给完成。

这个一一对应的设计看起来有些"浪费"——如果一个 PV 有 1Ti 容量，而一个 PVC 只需要 100Gi，剩下的 924Gi 就被闲置了。但这是为了保证**隔离性和可预测性**：一旦一个 Pod 声明它独占一个存储卷，它应该获得完整且不受干扰的访问权。共享卷可以通过 RWX 模式或更高层次的存储抽象来实现。

### 3.4 访问模式的现实约束

PV 和 PVC 中有三个访问模式：

- **ReadWriteOnce（RWO）**：卷只能被一个节点以读写方式挂载。这是限制最严格的模式，也是大多数块存储（如 AWS EBS、GCE PD）支持的默认模式。
- **ReadOnlyMany（ROX）**：卷可以被多个节点以只读方式挂载。适用于分发只读数据的场景（如模型文件、静态数据集）。
- **ReadWriteMany（RWX）**：卷可以被多个节点以读写方式挂载。这是最灵活但也最难实现的模式，通常需要网络文件系统（NFS）、CephFS 或 GlusterFS 等分布式存储。

访问模式不是 Kubernetes 定义的抽象概念，而是**底层存储系统的物理能力在 Kubernetes 层面的映射**。EBS 是块设备，协议层面就限制了一次只能挂载到一台 EC2 实例上，因此它只能支持 RWO。NFS 基于网络文件系统协议，多个客户端可以同时读写一个 NFS 导出，因此支持 RWX。

试图用 RWO 的卷运行多副本的 MySQL 集群，会得到明显的失败反馈——第二个 Pod 调度到不同节点后将无法挂载该卷。

## 4. 第三层抽象：从静态供给到动态自动化

### 4.1 静态供给的困境

在 PV/PVC 模式下，管理员需要预先创建好 PV。这意味着：

- 必须预判用户需要多大容量、什么类型的存储，并提前准备。
- 当应用需要一块 5Gi 的 NFS 存储时，管理员必须手动创建一块 5Gi 的 NFS 导出，并在集群中创建一个 PV 来对应它。
- 如果用户的需求超出了已有 PV 的容量或类型，他们只能等待管理员再创建一批。

在几十个应用的开发测试环境中，这勉强可以忍受。当集群规模增长到数百个应用，每个应用有不同的存储需求，静态供给的运维负担急剧上升。更重要的是，**公有云环境下，存储资源本身就是 API 管理的动态资源**——管理员手动创建 PV 再映射到云盘，相当于把云平台提供的自动化退化成人工操作。

解决方案很自然：让 Kubernetes 能够**自动创建**存储卷，而不是等待管理员手动创建。

### 4.2 StorageClass：存储的"配置模板"

StorageClass 就是用来描述"如何动态创建存储卷"的配置模板。它的核心字段包括：

- **provisioner（供给者）**：指定哪个存储后端负责创建实际的存储卷。在 AWS 上是 `ebs.csi.aws.com`，在 GCP 上是 `pd.csi.gke.io`，在 NFS 场景下可能是 `k8s-sigs.io/nfs-subdir-external-provisioner`。
- **parameters**：供给者的参数，如 `type: gp3`、`iopsPerGB: "10"` 等。
- **reclaimPolicy**：回收策略，决定 PVC 释放后 PV 如何处理（`Delete` 或 `Retain`）。
- **allowVolumeExpansion**：是否支持动态扩容。
- **mountOptions**：挂载选项，如 `"noatime"`、`"hard"`、`"nfsvers=4.1"`。

当用户在 PVC 中指定一个 StorageClass（通过 `storageClassName` 字段），并且该 PVC 创建时没有现有的 PV 可以匹配，集群的**动态供给机制**被触发：

1. Kubernetes 控制平面发现 PVC 需要动态供给。
2. 调用 StorageClass 中指定的 provisioner（通常是一个运行在集群中的 CSI 驱动）。
3. provisioner 向存储后端发起 API 调用，创建一个新的存储卷（如 AWS EBS 卷）。
4. 存储卷创建成功后，provisioner 自动创建一个对应的 PV 对象。
5. Kubernetes 将新创建的 PV 与 PVC 绑定。
6. Pod 得以正常启动，挂载这个新创建的卷。

整个过程在没有人工介入的情况下完成。这从"管理员预先准备好存储资源"的模式，转变为"用户声明需要存储，系统即时创建"的模式。

### 4.3 回收策略与生命周期管理

动态供给还引入了一个重要的问题：PVC 被删除时，对应的 PV 和底层存储卷该怎么处理？

回收策略给出了三种选择：

- **Retain（保留）**：PVC 删除后，PV 进入 `Released` 状态，底层存储卷保留。管理员需要手动清理和重用这些卷。这是最保守的策略，适合需要手动确认数据是否可清理的场景。
- **Delete（删除）**：PVC 删除后，PV 和底层存储卷一同被删除。这是动态供给的默认行为，适合临时性或测试环境。
- **Recycle（回收）**：已废弃。早期版本中用于简单清理后重新使用。

从 StorageClass 向下游传递回收策略，意味着存储的生命周期已完全纳入 Kubernetes 的控制体系：**从创建、绑定、使用到回收，Kubernetes 接管了存储卷的完整生命周期管理**。

### 4.4 延迟绑定：让调度与存储对齐

前面提到一个遗留问题：PV/PVC 的绑定发生在 Pod 被调度之前还是之后？这个时间点对调度结果有重要影响。

考虑以下场景：

- 集群中有两个节点，Node A 在可用区 us-east-1a，Node B 在 us-east-1b。
- 有三块云盘：PV-a 在 1a 区，PV-b1 和 PV-b2 在 1b 区。
- 用户创建一个 PVC，声明需要 100Gi。

默认情况下（`volumeBindingMode: Immediate`），PVC 创建后立即去寻找匹配的 PV。假设 PV-a 最先匹配成功，PVC 与 PV-a 绑定。然后 Pod 创建时只能被调度到 us-east-1a 区——因为只有 PV-a 在那里。如果 1a 区资源不足，Pod 就陷入 Pending 状态，即使 1b 区完全空闲。

问题的根源是：**PVC 绑定发生时，还不知道哪个节点会运行 Pod**。绑定的结果是存储位置被锁定，然后调度器只能在这个锁定的范围内寻找合适的节点。

StorageClass 引入了一个重要的参数 `volumeBindingMode: WaitForFirstConsumer`，即**延迟绑定**。在这种模式下，PVC 不会立即绑定 PV，而是等到第一个引用该 PVC 的 Pod 被创建时，调度器先选出合适的节点，然后**再根据节点的拓扑信息（如可用区）去绑定对应的 PV**。

这个过程确保了：

```
Pod 调度 → 确定节点 → 根据节点位置选择 PV → 绑定
```

而不是：

```
PVC 绑定 → 锁定存储位置 → 调度器受限 → 可能失败
```

延迟绑定是存储抽象从"独立于调度的静态匹配"向"感知调度动态决策"的重要演进。它填补了第二层抽象中"存储与调度之间"的缝隙。

## 5. 三层抽象的辩证关系

### 5.1 特性对比

| 维度 | emptyDir | hostPath | PV + PVC（静态） | PV + PVC + StorageClass（动态） |
|------|----------|----------|------------------|---------------------------------|
| 持久性 | Pod 删除后消失 | 节点上永久存在 | 独立于 Pod，Pod 删除后保留 | 独立于 Pod，可配置保留或自动删除 |
| 节点依赖性 | 无（任何节点均可） | 强（绑定到节点文件系统） | 取决于后端类型 | 取决于后端类型 |
| 可移植性 | 好 | 差 | 好（应用层不感知后端） | 最好（甚至不感知存储容量规划） |
| 管理介入 | 零 | 系统管理员级别 | 需要管理员预配置 PV | 只需定义 StorageClass |
| 适用场景 | 临时缓存、sidecar 通信 | 系统日志、特殊设备访问 | 生产级有状态应用 | 云原生弹性应用 |

### 5.2 选择的原则

这三层抽象并非取代关系，而是应对不同问题的垂直工具：

- 数据不需要持久化 → **emptyDir**，干净、轻量、零管理。
- 需要访问宿主机特殊文件或目录 → **hostPath**，但应仅限于系统级组件。
- 数据需要持久化且基础设施相对固定 → **静态 PV + PVC**，适合传统运维模式。
- 数据需要持久化且基础设施是动态的 → **StorageClass 动态供给**，云原生首选。

更准确地说，这四者并不在同一水平线上：emptyDir 和 hostPath 是**容器级**的卷挂载，PV/PVC 是**集群级**的存储抽象，StorageClass 是**供给策略级**的自动化层。每一层解决的是不同层面的问题，互不冲突，也没有一个"更高级"的存储类型能完全替代低级场景的需求。在同一个集群中，很可能同时存在所有类型的卷——sidecar 用 emptyDir 交换数据、Node Exporter 用 hostPath 读取宿主机指标、数据库用 PVC 引用动态供给的云盘。

## 6. 底层基础设施：CSI 与它的插件生态

上述所有抽象最终都需要落到具体的存储后端上。从 Kubernetes v1.13 起，**Container Storage Interface（CSI）** 成为容器与存储后端的标准接口。CSI 的核心思想与 OCI 如出一辙：制定一个标准化的接口契约，让任何符合 CSI 标准的存储驱动（如 AWS EBS CSI Driver、NFS CSI Driver、Ceph CSI Driver）都能无缝接入 Kubernetes。

CSI 驱动在集群中以 Pod 的形式运行，通过 gRPC 与 kubelet 和控制平面通信。当 PV 需要挂载时，kubelet 调用 CSI 驱动在节点本地执行挂载操作。整个架构分为三个部分：

- **Controller（控制器）**：运行在控制平面上，负责创建、删除、快照等管理操作（对应卷的"生命"）。
- **Node（节点插件）**：运行在每个节点上，负责挂载、卸载、格式化等操作（对应卷的"使用"）。
- **Identity（身份）**：声明驱动的标识和能力。

CSI 使存储后端的接入变成了一个"安装一个 Helm Chart"的操作，而不需要修改 Kubernetes 核心代码。这意味着新存储设备的接入周期从几个月缩短到几天，也使得社区生态空前繁荣。

## 7. 回顾：抽象的三次飞跃

回顾 Kubernetes 存储体系的演进，本质上是**三次从紧耦合到松耦合的抽象飞跃**：

1. **从容器到节点**（emptyDir / hostPath）打破了容器的文件系统隔离，但将存储绑定到了特定的节点上。
2. **从节点到集群**（PV / PVC）通过声明式的生产者-消费者模型，将存储从"节点资源"提升为"集群资源"，实现了存储与调度的分离。
3. **从静态到动态**（StorageClass）通过引入供给者模式，将存储供给从"人工操作"自动化，使得存储容量可以像计算资源一样按需分配，生命周期完全由 Kubernetes 管理。

这三次抽象遵循着 Kubernetes 一贯的设计哲学：**不消灭问题的复杂性，而是通过清晰的接口将复杂性隔离在可替换的模块中**。emptyDir、hostPath、PV、PVC、StorageClass 并不是相互替代的"存储类型"，而是围绕"容器需要访问数据"这一核心需求，在不同抽象层面给出的无重叠的解决方案。理解这些解决方案背后的设计动机——分别解决了什么矛盾、引入了什么约束、提供了什么权衡——远比记住它们的 YAML 字段更有价值。

当你下一次为一个有状态应用选择存储方案时，不妨这样思考：Pod 中的数据从哪来、到哪去？Pod 消失后这些数据是否需要存在？如果存在，它应该在哪里、以什么方式被访问？这些问题一步步引导你穿越 Kubernetes 存储的三层抽象，找到最适合你的答案。
