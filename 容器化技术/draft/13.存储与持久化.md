# 有状态应用的基石：Kubernetes 存储体系解析

> 容器生来无状态。但现实世界的应用需要数据留下来。本文梳理 Kubernetes 如何通过 Volume、PV/PVC、StorageClass、CSI 等一系列抽象，让容器环境也能优雅地管理数据。

## 1. 容器的临时性困境

容器被设计为**可丢弃的执行单元**——它的文件系统来自镜像的只读层，加上一个临时可写层。当容器被删除，可写层随之消失，所有写入的数据灰飞烟灭。这对无状态服务（如 Web 前端）不是问题，但对数据库、消息队列、日志系统等有状态应用来说，数据就是生命。

容器的临时性带来的三个核心矛盾：

- **数据持久性**：应用产生的数据如何在容器重启或删除后保留？
- **数据共享**：多个容器（尤其是同一个 Pod 内的容器）如何安全地读写同一份数据？
- **状态管理**：数据库这类有状态应用，如何在 Pod 漂移、节点故障时保证数据不丢？

Kubernetes 的回答是一整套分层存储体系。理解它，是驾驭有状态工作负载的关键。

## 2. 核心思路：将存储从 Pod 生命周期中解耦

K8s 存储体系的设计思想可以概括为一句话：**让存储活得比 Pod 长**。

实现这一目标，K8s 引入了几个关键抽象：

| 抽象 | 作用 | 谁在管 |
|------|------|--------|
| **Volume** | Pod 内的挂载点，定义数据从哪来、挂到哪 | 应用开发者定义 |
| **PV (PersistentVolume)** | 集群级别的存储资源，独立于 Pod 存在 | 集群管理员创建 |
| **PVC (PersistentVolumeClaim)** | 用户对存储的请求声明 | 应用开发者声明 |
| **StorageClass** | 存储的"分类"，自带动态供给能力 | 集群管理员定义 |
| **CSI** | 标准存储接口，让任意存储系统接入 K8s | 存储厂商实现 |

下面从最基础的 Volume 开始，逐层向上展开。

## 3. Volume：Pod 内数据的挂载方式

Volume 是 Pod 级别的存储抽象。它的生命周期与 Pod 绑定——Pod 存在，Volume 就在；Pod 删除，Volume 也随之消亡（除非使用持久化 Volume 类型）。Volume 的本质作用是为容器提供额外的存储目录，弥补容器文件系统的临时性缺陷。

### 3.1 emptyDir：Pod 内共享的临时空间

emptyDir 是 Pod 创建时分配的空目录，Pod 内的所有容器都可以读写它。Pod 被删除时，emptyDir 里的数据也随之清空。

它的典型用途是 Pod 内容器间的数据交换：一个边车容器负责从外部拉取文件写入 emptyDir，主容器读取同一目录处理业务。两个容器通过同一个 Volume 交换数据，无需走网络。

```yaml
volumes:
- name: shared-data
  emptyDir: {}
```

emptyDir 默认使用节点的磁盘，也可以指定 `medium: Memory` 将其挂载为 tmpfs（内存），速度更快但受限于节点内存容量。

### 3.2 hostPath：绑定到节点文件系统

hostPath 将宿主机上的文件或目录挂载到 Pod 内。Pod 删除后数据仍在宿主机上——但也因此存在明显的安全风险：Pod 可以读写宿主机文件系统。hostPath 不适合多租户集群或生产环境，仅建议在以下场景使用：

- 需要访问宿主机内核信息的 DaemonSet（如 `node-exporter` 读取 `/proc`）
- 单机开发测试环境

```yaml
volumes:
- name: host-log
  hostPath:
    path: /var/log
    type: Directory
```

### 3.3 configMap 与 secret：注入配置的 Volume

ConfigMap 和 Secret 作为 Volume 挂载，本质是将配置数据以文件形式呈现到容器的指定目录。Secret 与 ConfigMap 的区别在于：Secret 的值做了 Base64 编码（或加密），适合存放敏感信息。

挂载后，ConfigMap/Secret 中的每个 key 对应一个文件，其值就是文件内容。这种方式比环境变量更适合注入大量配置，且 K8s 会自动更新文件内容（有延迟），Pod 无需重启。

### 3.4 小结：临时 Volume 的适用边界

| Volume 类型 | 数据持久性 | 适用场景 |
|-------------|-----------|----------|
| emptyDir | Pod 删除即丢 | 临时缓存、容器间共享 |
| hostPath | 随节点持久 | 系统监控、开发调试 |
| configMap/secret | 由 API 对象管理 | 配置文件、凭据注入 |

临时 Volume 无法解决"Pod 漂移后数据还在"的问题。为此，K8s 引入了持久化存储体系。

## 4. PV 与 PVC：存储供给与使用的分离

PV（PersistentVolume）和 PVC（PersistentVolumeClaim）是 K8s 存储体系最核心的设计。它们实现了一个关键解耦：**存储的供给者（集群管理员）与使用者（应用开发者）通过声明式接口协作，互不关心对方的实现细节**。

### 4.1 PV：集群的存储资源

PV 是集群管理员预先准备的存储资源，独立于任何 Pod。它描述了存储的容量、访问模式、挂载类型和底层位置。

```yaml
apiVersion: v1
kind: PersistentVolume
metadata:
  name: nfs-pv
spec:
  capacity:
    storage: 10Gi
  accessModes:
    - ReadWriteMany
  nfs:
    server: nfs-server.example.com
    path: /exports/data
```

PV 有三个关键属性决定它能否被使用：

- **访问模式**：`ReadWriteOnce`（单节点读写）、`ReadOnlyMany`（多节点只读）、`ReadWriteMany`（多节点读写）。选择取决于存储后端的物理能力——NFS 支持 RWX，而 AWS EBS 只支持 RWO。
- **回收策略**：`Retain`（保留数据，需管理员手动清理）、`Delete`（自动删除底层存储）、`Recycle`（已废弃）。
- **存储类别**：通过 `storageClassName` 与 StorageClass 关联，决定匹配逻辑。

### 4.2 PVC：用户的存储申请

PVC 是应用开发者对存储的声明：我需要多少容量？什么访问模式？什么存储类别？K8s 控制平面会根据 PVC 的描述自动找到（或创建）匹配的 PV。

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: my-pvc
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 5Gi
  storageClassName: standard
```

### 4.3 PV 与 PVC 的绑定过程

PV 和 PVC 的绑定类似"插座与插头"：PVC 声明需求，控制平面中的 PersistentVolume Controller 遍历所有 PV，寻找满足容量、访问模式、存储类别三者匹配的 PV，建立绑定关系。绑定后，PVC 成为 PV 的"租户"，PV 的状态从 `Available` 变为 `Bound`。

如果当前没有匹配的 PV，有两种情况：

1. **静态供给**：PVC 保持 `Pending` 状态，直到管理员创建匹配的 PV，或已有 PV 被释放后重新匹配。
2. **动态供给**：如果 PVC 指定了 `storageClassName`，且该 StorageClass 支持动态供给，系统会自动创建 PV。

### 4.4 Pod 中使用 PVC

Pod 的 manifests 中引用 PVC，K8s 将对应的 PV 挂载到容器的指定路径。Pod 不再关心存储是 NFS、Ceph 还是云硬盘——这些细节被 PV/PVC 完全封装。

```yaml
volumes:
- name: data
  persistentVolumeClaim:
    claimName: my-pvc
```

这种解耦带来的实际好处是：**更换存储后端时，只需要改 PV 和 StorageClass 的定义，Pod 的 manifests 一行都不用动**。

## 5. StorageClass：存储的"商品目录"

如果说 PV/PVC 实现的是存储的"租赁关系"，那么 StorageClass 就是存储的"商品目录"——它定义了有哪些存储可供选择、每种存储有什么特性，并且能够自动按需创建 PV。

### 5.1 为什么需要 StorageClass

在没有 StorageClass 的时代，管理员必须预先创建大量 PV 等待使用。这种"静态供给"模式的问题很明显：

- **预测困难**：不知道应用需要多少存储，备少了不够用，备多了浪费。
- **响应慢**：应用需要新存储时，必须等待管理员手动创建 PV。

StorageClass 引入"动态供给"：开发者创建 PVC 时，系统根据 PVC 指定的 `storageClassName`，调用对应的 provisioner 自动创建 PV，并在 PVC 删除时自动销毁。这就把存储管理从"人工预配"变成了"按需自动分配"。

### 5.2 StorageClass 的结构

```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: fast
provisioner: kubernetes.io/aws-ebs   # 或 CSI 驱动名称
parameters:
  type: gp3
reclaimPolicy: Delete
allowVolumeExpansion: true
volumeBindingMode: WaitForFirstConsumer
```

关键字段：

- **provisioner**：决定由哪个存储后端来创建 PV。可以是内建的（如 `kubernetes.io/aws-ebs`），也可以是 CSI 驱动的名称。
- **parameters**：传给 provisioner 的参数，因存储后端而异。
- **reclaimPolicy**：动态创建的 PV 被释放后的处理方式，通常是 `Delete`。
- **volumeBindingMode**：`Immediate`（PVC 创建即绑定）或 `WaitForFirstConsumer`（等 Pod 被调度后再绑定）。后者对于云环境尤为重要——它能确保 PV 创建在 Pod 所在的可用区，避免跨 AZ 的 I/O 开销。

## 6. CSI：存储接入的标准化接口

StorageClass 解决了"动态供给"的问题，但每种存储后端都有一套自己的 provisioner 实现方式，各厂商各自为战。这就需要一套统一的接口标准——CSI（Container Storage Interface）。

### 6.1 CSI 的定位

CSI 是一个 gRPC 协议，定义了存储系统与容器编排系统之间的通用接口。任何存储厂商只要实现一套 CSI 驱动，就能无缝接入 K8s、Mesos、Nomad 等任意支持 CSI 的编排平台。

CSI 的核心包括三个 gRPC 服务：

- **Identity Service**：声明驱动的身份和能力（如是否支持快照、扩容）。
- **Controller Service**：控制面操作，创建/删除卷、创建/删除快照、卷挂载/卸载的控制面逻辑。
- **Node Service**：节点层面的操作，将卷格式化并挂载到 Pod 所在节点。

CSI 驱动以 DaemonSet + Deployment 的形式运行在 K8s 集群中，kubelet 通过 Unix Socket 与本机的 CSI Node 服务通信完成挂载操作。

### 6.2 为什么 CSI 是生态关键

CSI 出现之前，每种存储后端的接入方式都不一样。AWS EBS 用 in-tree 插件（代码嵌在 K8s 核心仓库），Ceph 用 flexVolume（外部二进制调用），NFS 靠内建支持。这种局面导致：

- K8s 核心仓库混杂着大量存储厂商的代码
- 厂商发版必须匹配 K8s 发版节奏
- 问题排查困难，每家的实现方式各不相同

CSI 之后，所有存储接入方式统一。厂商只需维护一个独立的 CSI 驱动，不依赖 K8s 版本。今天主流的存储后端——AWS EBS、Azure Disk、GCP PD、Ceph RBD、NFS、Longhorn、OpenEBS——都通过 CSI 驱动接入。这也成为各大云厂商提供块存储、文件存储、对象存储统一接入的事实标准。

## 7. StatefulSet 中的存储：从无状态到有状态

Deployment 管理的 Pod 是无状态的：每个 Pod 长得一模一样，PVC 模板共享，换掉一个 Pod 就像换掉一个一次性杯子。但数据库这类有状态应用恰恰相反——每个实例都有自己的数据，且不能混淆。

### 7.1 volumeClaimTemplates：为每个副本创建独立存储

StatefulSet 提供 `volumeClaimTemplates` 字段。每个 Pod 副本创建时，会自动生成一份独立的 PVC，命名格式为 `<volumeClaimTemplateName>-<podName>`。Pod 0 的 PVC 是 `data-mysql-0`，Pod 1 的是 `data-mysql-1`，一一对应，互不干扰。

```yaml
volumeClaimTemplates:
- metadata:
    name: data
  spec:
    accessModes: ["ReadWriteOnce"]
    storageClassName: fast
    resources:
      requests:
        storage: 20Gi
```

这意味着：即使 Pod 0 被删除并重新调度到其他节点，新 Pod 仍然会绑定到原来的 `data-mysql-0` PVC，数据不会丢失。这是 StatefulSet 比 Deployment 多出的关键行为——Pod 身份与存储的强绑定。

### 7.2 StatefulSet 存储的三大特性

1. **身份稳定**：Pod 有固定的网络标识和 PVC 绑定关系，重启或重调度后 Pod 身份不变，存储绑定不变。
2. **顺序约束**：Pod 按索引编号顺序创建、逆序删除。这为有状态应用提供了可控的启动和停止节奏。
3. **存储跟随**：每个 PVC 只绑定给一个 Pod，即使 Pod 被调度到不同节点，对应的 PV 也会通过存储后端的 detach/attach 机制跟随过去（前提是存储后端支持跨节点挂载）。

### 7.3 典型场景：MySQL 主从

MySQL 集群的每个实例需要各自的数据目录。StatefulSet 的 `volumeClaimTemplates` 为 master 和每个 slave 创建独立的 PV。当某个 slave Pod 所在的节点宕机，StatefulSet 在健康节点上重建同名 Pod，PVC 绑定关系让新 Pod 自动挂载原 PV，数据完好无损。

但有状态应用的管理远不止存储。MySQL 主从切换、故障恢复、备份恢复等操作，StatefulSet 本身不提供——这些需要 operator（如 `mysql-operator`、`vitess`）在 StatefulSet 之上实现。

## 8. 存储选型：从场景出发的决策框架

理解以上概念后，存储选型的本质是回答两个问题：**数据必须保留多久？数据需要被多少 Pod 同时访问？**

| 场景 | 推荐方案 | 考虑因素 |
|------|---------|----------|
| 临时缓存、日志暂存 | emptyDir | 随 Pod 生命周期，无需操心 |
| 单 Pod 持久化数据 | RWO PV + StorageClass | 适合大多数数据库、消息队列 |
| 多 Pod 共享读写 | RWX PV（NFS/CephFS） | 文件共享、媒体处理、CI 构建产物 |
| 配置注入 | ConfigMap/Secret volume | 只读挂载，热更新（有延迟） |
| 开发/单机环境 | hostPath 或 local PV | 简单直接，不涉及网络存储 |

选择持久化存储时，再向下追问一层：

- **延迟敏感型**（如数据库）→ 本地 SSD 或高性能云盘，RWO 模式
- **容量敏感型**（如日志归档）→ 对象存储 CSI 驱动或廉价文件存储，RWX 模式
- **可用性敏感型**（如生产数据库）→ 支持跨 AZ 复制的云存储，配合定期快照

## 9. 拓展路径：Go 深度绑定与 Operator 模式

对于常见业务场景，YAML 配置足以应对。但如果要深入定制存储策略，甚至构建自己的存储基础设施，有两种典型路径：

- **Go 客户端 + K8s 控制器模式**：通过 `client-go` 监听 PVC、PV、StorageClass 等资源事件，实现自动化存储运维。比如：自动将命名空间中未绑定 PVC 的 Pod 告警推送至工单系统；或根据业务水位自动调整 PVC 的 size 和 IOPS 上限。

- **自定义 Operator**：当 StatefulSet 无法满足有状态应用的运维需求（如自动备份、故障自动切换、扩缩容数据重分布）时，编写 Operator 接管整个生命周期。以 `mysql-operator` 为例，它会根据 CRD 中声明的集群规格，自动创建 StatefulSet 及其 `volumeClaimTemplates`，并在节点故障时协调主从切换——这些逻辑超出了原生 K8s 的能力范围。

## 10. 总结

K8s 存储体系的演进，本质是对"容器临时性"这一原罪的修补。从 emptyDir 到 PV/PVC，再到 StorageClass 和 CSI，每一层抽象都在提取共性问题、封装复杂性，让应用开发者只需关心"我需要什么样的存储"，而无需关心"存储从哪里来、怎么挂载"。

这套体系的核心价值在于解耦：

- **PV/PVC 解耦了存储的供给与使用**
- **StorageClass 解耦了存储的类别与创建方式**
- **CSI 解耦了存储后端的接入方式与编排系统**

掌握这套抽象层级之间的关系，是构建可靠有状态工作负载的前提。进一步可参阅 [[docs/容器运行过程|容器运行过程]] 理解运行时层如何与存储交互，或查阅 [[docs/K8s node 和 pod|K8s Node 和 Pod]] 了解 Pod 调度与存储亲和性策略。
