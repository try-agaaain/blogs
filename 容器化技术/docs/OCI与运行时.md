# 容器之心：OCI 规范与容器运行时技术深度解析

## 1. 标准化：从军阀混战到统一度量衡

2013 年 Docker 横空出世，把 Linux 内核中的 namespace、cgroups 等特性打包成“容器”这种易用形态，一时间风头无两。Docker 的成功引来众多追随者与竞争者——CoreOS 推出了 rkt，Mesos 有自己的容器化方案，各家云厂商也在构建自己的容器服务。每一个平台都在重复发明轮子，镜像格式互不兼容、运行时行为千差万别。当 Kubernetes 开始定义容器编排的版图时，它立刻触到了最大的痛点：**容器世界缺少一套中立的、可互操作的工业标准**。

2015 年 6 月，在 Linux 基金会的主导下，**Open Container Initiative（OCI）** 正式成立。它的使命很明确：制定容器镜像格式和运行时的标准，确保任何符合标准的镜像可以在任何符合标准的运行时上启动，且行为一致。这是容器生态从各自为战走向分工协作的关键一步。OCI 本身不生产软件，它定义“契约”，而社区则围绕契约构建繁荣的运行时引擎。

## 2. OCI 规范解剖：不仅仅是配置文件

OCI 维护着三个核心规范，它们像三本精密的工程图纸，共同规定了容器世界的基石。这三个规范分别是：**运行时规范 (Runtime Specification)**、**镜像规范 (Image Specification)** 以及**分发规范 (Distribution Specification)**。

如果说镜像是构建容器的“蓝图”，那么运行时规范就是让蓝图变成活生生进程的“施工说明”，而分发规范则定义了这些蓝图如何在全球的仓库间运输、验证和共享。三者合力，让容器的构建、运行、分发都有了统一的语言。

### 2.1 运行时规范 (Runtime Specification)

运行时规范定义了**容器的配置、执行环境和生命周期**。它的核心是一份 `config.json` 文件，运行时必须依据这份文件创建隔离环境。如果你熟悉 `runc spec` 命令，它生成的正是这份规范的标准参考实现。我们来拆解 `config.json` 的关键部分：

- **ociVersion**：遵循的规范版本，如 `1.1.0`。
- **process**：容器启动时的进程配置，包括启动命令 `args`、环境变量、工作目录、终端设置，以及至关重要的**用户身份** (`user`) 和**安全权能 (capabilities)** 。比如 `"capabilities": { "bounding": ["CAP_NET_RAW"], ... }` 精确控制容器内能执行哪些特权操作。
- **root**：指定根文件系统的路径（通常为 `rootfs`），以及是否只读。
- **mounts**：挂载点列表，从 `proc`、`sysfs` 这样的内核文件系统，到用户自定义的数据卷。规范严谨地定义了挂载选项、传播模式等。
- **linux**：Linux 平台特定配置，是整个规范的重头戏。它包含：
  - **namespaces**：一个数组，显式声明需要隔离的命名空间类型，如 `pid`、`network`、`mount`、`ipc`、`uts`、`user`、`cgroup`。如果 `network` 未列出，容器将与宿主机共享网络栈。
  - **resources**：cgroup 资源限制，定义 CPU 份额、内存上限、块 IO 权重等。这直接映射到 cgroup v1 或 v2 的控制器文件。
  - **seccomp**：系统调用过滤规则，可以指定默认动作为允许或拒绝，然后白名单或黑名单特定系统调用。
  - **maskedPaths** 和 **readonlyPaths**：内核层面的路径隐藏和只读保护，为容器提供纵深防御。
- **hooks**：定义了在容器生命周期特定阶段执行的钩子程序，如 `prestart`、`poststart`、`poststop`。这让网络插件或自定义初始化脚本可以无缝注入，而无须侵入运行时本身。

运行时规范还规定了容器必须经历的标准生命周期操作：**创建 (create)**、**启动 (start)**、**终止 (kill)**、**删除 (delete)**，以及查询状态 (`state`)。这套状态机保证了任何 OCI 兼容运行时都有可预测的行为。更关键的是，运行时通过一个简单的文件系统接口（如 unix socket）传递状态，上层控制器可以据此管理容器。

### 2.2 镜像规范 (Image Specification)

镜像规范规定了容器镜像的存储和传输格式，解决了“一个镜像到处运行”的互操作问题。镜像本质上是一组只读的、叠加在一起的文件系统层及其元数据的集合，它描述的是**静态的模板**；而容器则是把镜像提供的文件系统作为根文件系统，再叠加一个可写层，并注入进程、网络、资源限制等运行时要素后形成的**动态实例**。这一静一动的关系，贯穿整个容器技术。

镜像规范主要由以下部分构成：

- **清单 (Manifest)**：一个 JSON 文件，记录镜像的元信息，包括配置对象（指向镜像配置）、层数组（指向实际的 tgz 层文件）。清单提供了多架构支持——同一个镜像名可以对应不同 CPU 架构的清单。
- **镜像索引 (Image Index)**：一个更高阶的清单列表，允许一个“镜像名”通过索引选择特定平台的清单。这是多架构镜像（如 `amd64` / `arm64`）的桥梁。
- **镜像配置**：包含运行时需要的默认参数（环境变量、入口点、命令）、暴露的端口、卷声明，以及层的差异配置（如历史信息、创建时间）。
- **文件系统层**：每个层都是一个 tar 压缩包，包含相对于根文件系统的增删改文件。层之间通过链式组合形成完整的 rootfs。层的内容存储为内容可寻址的 blob，其摘要 (digest) 作为唯一标识，保证了完整性。

镜像规范定义了从注册中心推拉镜像、将镜像解包到根文件系统的通用方式。任何人只要遵循这套格式，就可以构建与 Docker Hub 兼容的注册中心，或者用 `skopeo` 这样的工具在不同存储间复制镜像，而无需任何 Docker 守护进程。

### 2.3 分发规范 (Distribution Specification)

镜像规范解决的是“镜像如何打包”，而**分发规范**解决的是“镜像如何运输和发现”。它定义了一套标准的 HTTP REST API，使得任何 OCI 兼容的注册中心（如 Docker Hub、Harbor、Amazon ECR）都能以统一方式完成以下操作：

- **推送镜像** (`POST /v2/<name>/blobs/uploads/`)：将层 blob 和清单上传到仓库。
- **拉取镜像** (`GET /v2/<name>/blobs/<digest>`)：通过内容摘要下载层文件，并拉取清单。
- **内容发现** (`GET /v2/<name>/tags/list`)：列出镜像的所有标签。
- **认证与授权**：通过 Bearer token 挑战机制，保障仓库的安全性。

分发规范让 `skopeo` 这样的工具能够在不同注册中心之间直接复制镜像，无需 Docker 守护进程参与；也让 `oras` 项目可以将任何文件（如 AI 模型、Wasm 模块）以 OCI Artifacts 的形式推送到同一套基础设施中。至此，运行时、镜像、分发三大规范构成闭环：**镜像规范定义格式 → 分发规范定义传输 → 运行时规范定义执行**。

## 3. 运行时分层：低级与高级的清晰边界

OCI 三大规范定义了容器世界的“语言”，而真正的运行环境则呈现清晰的分层结构。下面这张图揭示了从用户指令到内核的完整路径：

```
┌─────────────────────────────────────────┐
│        Kubernetes / Docker CLI          │
├─────────────────────────────────────────┤
│   containerd / CRI-O  (高级运行时)       │
│  - 镜像拉取，rootfs准备，生成config.json │
├─────────────────────────────────────────┤
│   OCI 运行时接口 (shim / cmd 调用)       │
├─────────────────────────────────────────┤
│   runc / crun / youki   (低层运行时)     │
│  Kata Containers / gVisor (沙盒运行时)   │
├─────────────────────────────────────────┤
│  Linux 内核 (cgroup, namespace, KVM...) │
└─────────────────────────────────────────┘
```

标准的出现让这个分层架构自然分化为：

- **低级运行时 (Low-Level Runtime)**：直接遵照 OCI 运行时规范，从 `config.json` 创建并运行容器的轻量级程序。它们与内核打交道，负责创建 namespace、设置 cgroup、置入 seccomp 策略等。范例就是 `runc` 和 `crun`。
- **高级运行时 (High-Level Runtime)**：提供守护进程、gRPC API、镜像管理、网络插件、存储快照、多容器生命周期管理等完整功能。它们并不直接运行容器，而是委托低级运行时执行，自身专注于编排、服务暴露和开发体验。典型的代表是 `containerd` 和 `CRI-O`。

这种分层像操作系统的微内核架构：`runc` 类似内核，处理最底层细节；`containerd` 类似系统服务，把复杂的镜像下载、解压、网络分配等脏活累活抽象成简单 API。这种解耦允许自由替换——你可以把 Docker 默认的 `runc` 换成安全性更强的 `kata-runtime`，而无需改变上层的容器管理逻辑。

## 4. 低级运行时：runc、crun 与运行原理

### 4.1 runc：血脉正统的奠基者

`runc` 是 OCI 运行时规范的参考实现，由 Docker 捐献的 `libcontainer` 演变而来，使用 Go 语言编写。它的职责极其单一：给定一个 OCI 配置和 rootfs 路径，启动容器进程。

运行过程核心步骤简化如下：

1. `runc create` 被调用，runc 会 fork 出自身，然后通过 Go 标准库的 `syscall.RawSyscall` 调用 `clone` 系统调用，传入一系列 `CLONE_NEW*` 标志来创建新命名空间。此时子进程拥有全新的 PID、网络、挂载等视图，但尚未执行用户命令。
2. 在子进程内，runc 依据 `config.json` 设置 `hostname`（UTS namespace）、挂载 `/proc`、`/sys` 以及用户指定的挂载点；设置 cgroups 资源限制；应用 seccomp 过滤规则和 capabilities。
3. 完成环境初始化后，子进程通过管道通知父进程自己已准备好。父进程记录容器状态后退出，子进程在等待 `runc start` 信号。
4. 用户执行 `runc start`，runc 通过 exec fifo 向容器子进程发送指令，子进程最终执行用户指定的应用命令（如 `/bin/sh`）。此时容器主进程开始运行。

这种分离的 `create` / `start` 动作允许在容器正式启动前完成复杂的网络配置（比如先将容器端 veth 加入到网桥）。但 runc 的一个问题在于：容器进程由 runc 直接创建，runc 是容器进程的父进程。如果 runc 退出，容器会变为孤儿？这里就引出了 **容器 shim** 的必要——高级运行时会启动一个 shim 进程作为中介，runc 启动完成后即退出，而 shim 接管容器的 STDIO 和 exit code。这将在 containerd 部分详述。

### 4.2 crun：用 C 语言重写的速度利器

`crun` 由红帽工程师发起，完全用 C 语言实现，目标非常聚焦：**更快、内存占用更低、cgroup v2 原生支持**。

- **性能**：`crun` 没有 Go 运行时的负担，无需 GC，二进制体积小，启动延迟显著低于 `runc`。尤其在大量并发启动容器的场景下，其性能优势突出。
- **cgroup v2 完备性**：虽然 runc 也支持 cgroup v2，但 `crun` 作为较新的项目，从设计之初就以 cgroup v2 为中心，对 `cgroup.subtree_control`、`cgroup.controllers` 等接口的使用更加自然彻底，能够充分利用统一层次结构的特性。
- **内存开销**：每个容器创建过程中，`crun` 自身消耗的常驻内存极低（约 1-2 MB），适合资源受限环境或极大规模容器密度。

兼容性上，`crun` 完全符合 OCI 运行时规范，且通过 containerd 的 shim 可以无缝替换 runc。如今许多 Kubernetes 发行版已将默认运行时切换为 `crun`，因为它兼顾了轻量与标准。

### 4.3 安全增强的异类：Kata Containers 与 gVisor

标准容器共享内核，一旦内核出现提权漏洞，容器隔离就形同虚设。这催生了基于硬件虚拟化的 OCI 运行时。

- **Kata Containers**：将每个容器运行在一个裁剪过的轻量级虚拟机内，使用 Intel VT-x 或 AMD-V 硬件隔离。它的运行时 `kata-runtime` 完全兼容 OCI，通过 containerd 的 shim v2 接入。Kata 使用 `QEMU` 或 `firecracker` 作为 VMM，并搭配专为容器优化的极简内核。每个容器拥有独立内核，安全边界等同于虚拟机，但启动速度远快于传统 VM（约 100-300ms）。Kata 牺牲了一定密度和文件系统弹性，换取多租户云环境需要的强隔离。
- **gVisor**：采用另一种思路——在用户态实现了一个用 Go 编写的内核（Sentry），拦截应用的系统调用并自行处理，大多数系统调用根本不落入宿主机内核。这样无需硬件虚拟化，即可在低开销下获得较强隔离。gVisor 的 `runsc` 也是一个 OCI 兼容运行时。

这些安全容器运行时能在不影响上层编排的情况下，通过替换容器 shim 来为 Pod 提供不同的安全等级，是 OCI 生态多样性的最佳体现。

## 5. 高级运行时：containerd 与 CRI-O

高级运行时是容器平台的“大管家”，它们将底层 runc/crun 的复杂性包装成整洁的 API，并补齐了镜像传输、存储、快照和网络等功能。

### 5.1 containerd：从 Docker 走出的业界标准

`containerd` 原为 Docker 内部的容器执行层，2017 年捐赠给 CNCF 并独立发展。它是一个以守护进程形式运行的高性能容器管理器，专注于运行容器、推送/拉取镜像、管理存储和网络的基本原语。

**核心架构**：

- **Client / Daemon**：提供 gRPC 接口，客户端通过定义的 service（如 `Containers`, `Tasks`, `Images`）与 daemon 交互。Kubernetes 的 CRI 插件、`ctr` 工具、`nerdctl` 都是其客户端。
- **Snapshots**：用联合文件系统（overlayfs）或 devicemapper 管理容器层的快照器。镜像被解包为快照，容器启动时在快照栈上添加一个可写层。**这也正是镜像与容器在文件系统层面的区别：镜像是一系列只读快照的叠加，而容器则是在这些只读层之上再挂载一个可写层，成为运行时的文件系统。**
- **Images**：拉取并存储 OCI 镜像，内容寻址存储保证了层不会被重复存储。
- **Content Store**：存储 blob 的键值库，确保数据和元数据一致。
- **Tasks 与 Shim**：这是 containerd 设计的精妙之处。当你请求启动一个容器，containerd 会先启动一个与容器生命周期绑定的 shim 进程（通常为 `containerd-shim-runc-v2`），然后 shim 调用 `runc create/start` 来启动容器进程。`runc` 在完成启动后**立即退出**，shim 继续维持容器进程的 stdin/stdout/stderr 管道，并且作为容器进程的父进程回收退出状态。这样使得 containerd 自身的重启不会影响正在运行的容器（因为 shim 独立于 daemon）。同时，每个 shim 可以对接不同的底层运行时——只要实现 shim v2 协议，即可使用 kata、gVisor、甚至 future 的 Wasm 运行时。
- **CRI Plugin**：内嵌了一个 CRI（Container Runtime Interface）服务，直接接收 kubelet 的 pod 操作指令，无须额外安装适配器。

containerd 功能完善，但在镜像构建、卷管理、编排等高级功能上完全退后，让 Docker 自身或 nerdctl 在更高层提供。这种克制让其成为 Kubernetes 最通用的容器运行时。

### 5.2 CRI-O：为 Kubernetes 而生

`CRI-O` 的目标极其纯粹：实现 Kubernetes CRI，其他一概不要。它没有构建镜像的命令（`build`），没有 Docker Compose 的支持，甚至没有独立的 CLI（使用 `crictl` 通过 CRI 接口进行管理）。它的全部设计围绕一个中心：**如何以最高效、最安全的方式运行 Kubernetes Pod**。

CRI-O 直接管理 OCI 镜像的拉取和存储，同样使用 `containers/storage` 和 `containers/image` 库，并为每个 Pod 创建一个带暂停容器的环境。它直接调用 `runc` 或 `crun`（通过类似 shim 的 `conmon` 监控进程）运行容器。它的优势在于代码库更小、攻击面更窄，特别适合那些只需要 K8s 工作负载的硬核环境。在 OpenShift 等平台，CRI-O 是默认运行时。

**containerd vs CRI-O**：containerd 源于 Docker 生态，功能范围更广，社区成熟度极高；CRI-O 是 K8s 原生运行时，轻量且专一。两者都通过 CRI 接口与 kubelet 交互，对上层应用完全透明。由于 containerd 已经内置了 CRI 插件，部署更简单，因此成为众多发行版的首选。

## 6. OCI 如何撬动未来

OCI 这座标准化大厦，为容器生态带来了三个深远影响：

1. **避免厂商锁定**：任何符合 OCI 的镜像可运行在任何符合 OCI 的运行时上，从 Linux 容器到 Windows 容器，再到新兴的 Wasm 运行时，都共享同一套分发标准。你可以今天用 `runc`，明天无缝迁移到 `kata` 或 `crun`，编排层无感。
2. **催化创新**：运行时不再是一家独大。除了上面提及的安全容器、C 语言运行时，现在社区可以尝试用 Rust 实现的 `youki`，或针对 Serverless 优化的 `firecracker-containerd`。这期间 OCI 规范确保了基本互操作性。
3. **跨领域伸展**：Wasm 运行时如 `wasmtime` 通过 OCI 镜像分发 Wasm 模块；边缘设备上用 `crunn` 等超轻量运行时在资源有限环境下运行 OCI 容器。镜像规范甚至被用于 AI 模型的分发（OCI Artifacts），因为其层管理和内容寻址设计非常适用于大文件版本化。

回望当初，如果没有 OCI，Kubernetes 可能还锁死在某个特定运行时上，而无法发展出今天百花齐放的 CRI 生态。低级运行时处理“容器 = 进程+命名空间+cgroup+安全策略”的本质，高级运行时管理镜像、网络和生命周期，安全运行时重新定义隔离边界——它们由标准契约紧密联结，共同构成现代云原生的基座。

当你在 yaml 里写下一个 `image: nginx:latest`，背后是 OCI 分发规范从仓库中拉取清单和一系列只读层，是镜像规范将这些层组合成静态的根文件系统模板，是 containerd 或 CRI-O 将其解压为快照并生成 `config.json`，最后是 `runc` 或 `crun` 用一段精心设计的 `clone` 调用，为这个模板注入进程、命名空间和一切运行时约束，在一瞬间创造出那个看似平凡却极致精密的隔离世界——一个真正的容器。这便是容器运行时技术深度之美。
