# 拆解容器运行的黑盒：从 Docker 到沙盒进程，一条命令的完整执行路径

当你习惯性地敲下 `docker run -d nginx`，一个隔离的容器便出现在系统中。这条命令的执行，实际上经过了 **daemon、高级运行时、shim、OCI 运行时包装器、低级运行时** 五个层次的协作。有人可能觉得这是“过度工程化”，但每一层都对应着明确的生产需求。

本文以 Docker 生态为主线，兼谈 Kubernetes 下的 CRI 变体，串联起这些核心概念，最终呈现出一条清晰的容器启动流水线。

## 一、容器运行时的分层模型

为了理清思路，我们先界定几个关键概念。通常容器运行时被划分为高层和低层，而 shim 和 daemon 则充当它们之间的粘合剂。

- **Daemon（守护进程）**：常驻后台的服务，接收用户请求，管理镜像、网络、存储卷等生命周期。代表是 `dockerd`。
- **高级运行时（High-level Runtime）**：面向容器镜像、网络、存储等高层语义，负责下载镜像、解压 rootfs、准备挂载等。代表是 `containerd`、`CRI-O`。它们通常通过 gRPC 对外提供 API。
- **shim（垫片进程）**：一个轻量级进程，负责维持容器进程的存活，并解除 daemon 与容器生命周期的强耦合，使 daemon 重启时容器不受影响。
- **低级运行时（Low-level Runtime）**：依据 OCI 规范文件，调用 Linux 内核的 namespace、cgroup 等机制创建隔离进程。代表是 `runc`、`crun`。
- **OCI 运行时包装器（OCI Runtime Wrapper）**：自身表现为一个 OCI 兼容的低级运行时，但会在真正低级运行时前后添加额外处理，例如 GPU 设备注入或启动虚拟机。代表是 `nvidia-container-runtime`、`kata-runtime`。

下面沿着完整的调用链，逐步剖析各层之间的协作方式。

## 二、起点：Daemon 与用户的交互

用户执行 `docker run`，Docker 命令行工具（CLI）并非直接去启动容器，而是把你提供的镜像、端口、挂载卷等参数封装成一个符合 RESTful 风格的 HTTP 请求，通过本机上的 Unix 套接字文件 `/var/run/docker.sock` 发给后台常驻的 Docker 守护进程（**dockerd**），最终由 **dockerd** 接收该请求并真正完成容器的创建与运行。

`dockerd` 是总入口。它管理所有容器对象的元数据，并负责卷、网络、镜像拉取等高级编排。但从 Docker 1.11 起，它已不再直接创建容器进程，这一职责被转交给 `containerd`。

调用流程如下：

```
docker CLI --> dockerd (daemon) --> containerd (高级运行时)
```

这样拆分的原因是，`dockerd` 功能庞杂，还需处理构建、认证、Swarm 等。将容器生命周期管理提取为独立的 `containerd`，既让 Docker 自身更模块化，也为 Kubernetes 通过 CRI 对接 containerd 打下基础。

在此过程中，当需要拉取镜像时，dockerd 会依据 **OCI 分发规范** 与镜像仓库（registry）进行通信。

## 三、高级运行时：从镜像到沙盒规格

`containerd` 收到创建容器的指令后，展现高级运行时的完整功能：

1. **镜像管理**：下载镜像，将分层镜像解压、合并，准备好容器的 rootfs。这些镜像在构建时严格遵循 **OCI 镜像规范**，无论是 Docker 构建的镜像还是其他工具构建的 OCI 镜像，containerd 都能无差别地解析和使用。
2. **准备 OCI 规格文件（config.json）**：关键步骤。将用户提供的参数（入口命令、环境变量、挂载、资源限制等）转换为符合 **OCI 运行时规范** 的 JSON 文件。该文件相当于一个精确的配置声明，低级运行时据此创建容器。
3. **调用低级运行时**：containerd 本身不操作 namespace，必须将规格文件交给实现了 OCI 运行时接口的二进制（如 `runc`）。

此时，如果 containerd 直接 fork 出 `runc` 并等待容器结束，会引发一个严重问题：containerd 重启后，将丢失原有容器的进程状态，容器可能成为僵尸进程或被误杀。

因此，引入了 **shim**。

## 四、shim：解除容器与 daemon 的耦合

containerd 的做法是：为每个容器先启动一个 **containerd-shim** 进程，再由 shim 去调用低级运行时。

shim 的职责非常单一：

- 作为容器进程的父进程（或祖先进程），接管其 stdin/stdout/stderr 管道。
- 以守护方式维持容器状态，容器退出后报告退出码。
- 即便 containerd 甚至 dockerd 重启，只要 shim 仍在，容器进程就不受影响。

调用链变为：

```
dockerd --> containerd --> containerd-shim --> runc (低级运行时)
```

`runc` 完成容器创建后即可退出，容器内 PID 1 进程由 shim 接管。此时，即使停止 dockerd 和 containerd 再重启，它们只需重新连接到存活的 shim，即可恢复所有容器的管理。这为容器引擎的无缝升级提供了基础。

## 五、低级运行时：通过内核机制创建容器

接力棒传到 **runc**。它读取 shim 传入的 OCI 规格文件，按步骤构建容器环境：

1. **设置 namespace**：通过 `clone()` 或 `unshare()` 系统调用，创建独立的 PID、UTS、网络、挂载等命名空间。
2. **设置 cgroup**：根据资源限制，在 cgroup 文件系统中写入 CPU、内存等限制值。
3. **切换 rootfs**：通过 `pivot_root` 或 `chroot`，将进程根目录切换到容器镜像的根文件系统。
4. **应用安全配置**：如 `seccomp`、`capabilities`、`SELinux` 标签等。
5. **执行用户命令**：最后通过 `exec` 运行用户指定的入口程序（如 nginx）。

`runc` 并不常驻，它创建完容器即退出。正因如此，才需要 shim 在后台维持容器状态。

此外，`crun` 作为 C 语言实现的低级运行时，内存占用更小、速度更快，但功能与 runc 一致。两者均遵循 OCI 运行时规范，可互换使用。

## 六、OCI 运行时包装器：在 runc 之前插入可编程逻辑

如果架构到此为止，容器运行时栈就过于简单了。生产环境的复杂需求催生了 **OCI 运行时包装器**。

OCI 规范规定，运行时二进制接受 `create`、`start`、`delete` 等子命令。这个接口是标准的，意味着可以实现一个程序，它对外表现为 OCI 运行时，内部则进行任意预处理，再将实际工作委托给真正的 runc。这便是包装器的核心思想。

### 场景一：GPU 容器 —— nvidia-container-runtime

AI 容器需要访问 NVIDIA GPU。若直接使用 runc，需手动挂载 GPU 设备文件、驱动库，并注入环境变量和依赖，操作极其繁琐。

NVIDIA 提供了 `nvidia-container-runtime`。当 Docker/containerd 配置 `--runtime=nvidia` 时，实际调用的是这个包装器。它执行以下三步：

1. 读入原有 OCI 规格文件。
2. 调用 **nvidia-container-cli**，自动发现所需的 GPU 驱动文件和设备节点，生成额外的挂载与环境变量，并修改 OCI 规格。
3. 调用真正的低级运行时 `runc`，并传入修改后的规格文件，创建容器。

对 containerd 而言，它只是在调用一个标准的 OCI 运行时；而对用户来说，GPU 资源已透明可用。

### 场景二：安全沙箱 —— kata-runtime

若要实现强隔离，将容器运行在微型虚拟机中，`kata-runtime` 是另一个典型的包装器。它同样实现 OCI 运行时接口，但在执行 `create` 时并非直接创建 Linux 容器，而是：

1. 启动一个轻量级虚拟机（基于 QEMU 或 Firecracker）。
2. 在虚拟机内启动精简内核和 agent。
3. agent 在 guest 内部根据 OCI 规格创建具有命名空间隔离的进程。
4. 将容器的 stdio 重定向到宿主机的 shim。

高级运行时（如 containerd）和 shim 几乎无需改动，仅需更换运行时配置，就能将“共享内核”的容器无缝切换为“硬件虚拟化”的沙盒。

**OCI 运行时包装器** 起到了“插入式扩展点”的作用：它赋予运行时可编程性，从注入设备到虚拟化隔离，均可实现，且不影响上层编排。

## 七、全景图：一条命令的全栈串联

将以上所有角色放入一张全景图，从用户发起请求到容器进程诞生的完整流水线如下：

```
用户
  │ docker run
  ▼
dockerd  (daemon: 接收命令，负责编排)
  │ gRPC
  ▼
containerd  (高级运行时: 下载镜像，准备 rootfs，生成 OCI 规格)
  │ fork + exec
  ▼
containerd-shim  (shim: 轻量级守护，维持容器生命周期)
  │ exec (可选 OCI 运行时包装器)
  ▼
nvidia-container-runtime / kata-runtime  (修改 OCI 规格，完成特殊处理)
  │ exec
  ▼
runc / crun  (低级运行时: 创建 cgroup/namespace，切换 rootfs，执行用户进程)
  │
  ▼
容器进程 (nginx)  ◄── 由 shim 托管
```

在这个架构中，每一层均遵循单一职责：

- **Daemon** 负责全局管理。
- **高级运行时** 负责镜像管理与规范转换。
- **shim** 负责进程生命周期与 I/O。
- **OCI 包装器** 负责扩展与附加处理。
- **低级运行时** 负责实际的容器创建。

## 八、Kubernetes 视角的变体

在 Kubernetes 环境中，调用链略有变化，但抽象分层一致：

- kubelet 通过 **CRI (Container Runtime Interface)** 调用高级运行时，如 containerd 或 CRI-O。
- containerd 内部仍使用 shim + runc（或所配置的任意 OCI 运行时）。
- 为了支持 Pod 内多容器共享网络和存储命名空间，引入了 **pause 容器**（一个长期挂起的沙箱），业务容器通过加入其命名空间共享网络栈。

核心底层（shim、低级运行时、OCI 包装器）的角色没有任何改变。可以认为 Docker 是 CRI 的一种早期实现，而 containerd 是其中的核心子集。

## 九、总结：分层架构实现无中断升级与运行时解耦

回顾整条调用链，层数可能显得较多。但正是这些抽象，为现代容器平台带来了两项关键能力：

1. **无中断升级**：shim 使守护进程的重启与容器运行解耦，升级 Docker 或 containerd 时，线上容器不受影响。
2. **运行时可替换性**：OCI 标准接口允许低级运行时在 runc、crun、kata、gVisor、Firecracker 甚至自定义运行时之间自由切换，上层编排系统无需修改代码。

理解这些关系后，容器不再是“黑盒”。你可以清楚知道：设置 `--runtime=nvidia` 时，究竟改变了哪个环节；containerd 崩溃时，为什么容器仍能继续运行。

容器运行时的各个组件职责清晰、紧密协作，共同构成了云原生基础设施的基石。
